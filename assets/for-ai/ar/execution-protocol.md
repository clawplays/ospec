# بروتوكول تنفيذ الذكاء الاصطناعي (طبقة تحكم goal)

هذه الوثيقة هي المرجع الموثوق خلف مهارة `ospec-goal`، وليست وثيقة دخول. القواعد التشغيلية التي تعمل بها موجودة في المهارة؛ ولا تفتح هذا الملف إلا عندما تظهر حالة محددة بالاسم — بدائيات الانتظار الأصلية لكل harness وانتهاء صلاحية lease، وتقارب إصلاح review ونطاق finding العابر للمهام، ودلالات CAS في allowlist، وتأجيل القبول الخارجي، والأرشفة القسرية، أو أي قاعدة تذكرها المهارة دون أن تفصّلها بالكامل. لا تحمّلها عند الدخول إلى `workflow_profile_id: goal` ولا عند بدء عمل `ospec execute …` / `ospec loop …`. أما في classic change فاتبع `for-ai/change-protocol.md` بدلاً منها ولا تحمّل هذا الملف إطلاقاً: فذلك الملف يحمل عقد بوابات القرار وعقد الأرشفة القسرية الخاصين بـ classic change كاملين، ولذلك لا يحتاج profile الـ change أي شيء من هنا.

هذه النسخة المعتمدة داخل المشروع من مواصفة OSpec الأم. اتبعها بدلاً من الارتجال انطلاقاً من المستودع الأم؛ وعند اختلاف قواعد المشروع عن المواصفة الأم تكون الأولوية للقواعد المعتمدة داخل المشروع.

## ترتيب القراءة

تحمل مهارة `ospec-goal` هذا الترتيب نفسه، وتلك النسخة هي المستخدمة فعلياً عند الدخول؛ وهو مسجَّل هنا بوصفه المصدر الموثوق، لا سبباً لفتح هذا الملف أولاً.

1. `.skillrc`
2. اقرأ `.ospec/session-brief.md` إذا كان موجودا؛ وإلا شغّل `ospec session [path]` في المشاريع المهيأة لإنشائه
3. كل ما عدا ذلك عبر `ospec index query <كلمات...>` وbrief أو dispatch packet الحالي: لا تقرأ `SKILL.index.json` كاملاً أبداً (فهو ينمو بلا حد مع أرشفة التغييرات)، واستخدم الفهرس لتحديد موقع المعرفة قبل قراءة الملفات الهدف، ولا تفتح إلا ما تسميه المرحلة الحالية — change artifacts الخاصة بها والملفات المستهدفة وملفات `SKILL.md` ذات الصلة ووثائق المشروع أو الأرشيف المفهرسة والقواعد المعتمدة للمشروع تحت `for-ai/` (`naming-conventions.md` و`skill-conventions.md` و`workflow-conventions.md` و`development-guide.md`). ولا تحمّل جميع goal artifacts افتراضياً

## القواعد الإلزامية

- اكتب كل مخرج change تنشئه — الوثائق وbrainstorms وartifacts الخاصة بـ goal — بلغة وثائق المشروع (`documentLanguage` في `.skillrc` / إرشادات `for-ai/` المُدارة): لا تستنتج اللغة من واجهة المنتج أو locale الموقع أو متطلب "الإنجليزية أولاً"، ولا تبدّل change بدأ بالفعل ما لم تنص قواعد المشروع على ذلك صراحةً، ولا تخلط اللغات داخل change واحد
- لا تتجاوز الملفات والبوابات المطلوبة للـ workflow profile الحالي وتدّعي الاكتمال مباشرة
- عند الدخول إلى مشروع OSpec موجود، استخدم `ospec session [path]` لكتابة `.ospec/session-brief.json` و`.ospec/session-brief.md`؛ يسجل profile ‏`change` أو `goal` للعمل النشط وqueued changes وحالة queue-run وcache fingerprint والأوامر الآمنة التالية الموافقة للـ profile فقط، ولا يشغّل workers ولا tests ولا يفحص git ولا يؤرشف ولا يحرر source files. ولا تستخدم `ospec session hook [path]` إلا لكتابة hook artifacts اختيارية لبدء جلسة الـ harness بالتوجيه ومصادر بوابات القرار نفسها
- استخدم `ospec brainstorm [path] --topic "..."` فقط لملفات الاستكشاف الاختيارية قبل change تحت `.ospec/brainstorms/`؛ ويضيف `--visual` رفيقاً محلياً بصيغة HTML ثابتة، والأمر لا ينشئ change. واستخدم `ospec plan [path] --change changes/active/<change>` لمسودات الخطة الاختيارية تحت `.ospec/plans/`، ولا تمرر `--apply` إلا عند تحديث `implementation-plan.md` لذلك change عن قصد
- تعامل مع خطوات built-in quality policy المفعّلة مثل `tdd_cycle` و`root_cause_debug` و`verification_evidence` كـ `optional_steps` خاضعة لـ archive gate؛ غطّها في `tasks.md` و`verification.md` وملفات evidence المطابقة قبل closeout
- طبقة التحكم `ospec execute …` (bootstrap وpreflight وdispatch وlaunch وreview وworktree وfinish وcollect وretry وsync) وكل artifacts الخاصة بـ goal تنتمي إلى `workflow_profile_id: goal`، ولا تدخلها إلا عندما يختار المستخدم Goal صراحة (`ospec goal` / `ospec-goal`). وإذا كان profile الحالي هو `change` فتوقف هنا واتبع `for-ai/change-protocol.md`
- أنشئ `design.md` أو حدّثه بنفسك بعد `proposal.md` وقبل تعديل `implementation-plan.md` أو `tasks.md` أو الكود؛ ولا تطلب من المستخدم كتابة `design.md` أو `implementation-plan.md` يدوياً، بل اشتقهما من المتطلب و`proposal.md` وسياق المشروع
- `Announce-Before-Act`: لا تُشغّل سير العمل بصمت. أعلن OSpec skill والمرحلة، والأمر والـ artifact، وmodel-native subagent adapter المختار، وعدد workers، وcurrent session capability، وأي بوابة تحجب التقدم
- `Brainstorm-First`: ابدأ كل goal بجولة عصف ذهني قصيرة قبل تثبيت التصميم. اعرض الأسئلة المفتوحة حول الاتجاه والبنية وAPI والبيانات وUI والمخاطر والنطاق، واسأل المستخدم سؤالاً واحداً في كل مرة بدلاً من الافتراض الصامت؛ واحفظ الاستكشاف عبر `ospec brainstorm [path] --topic "..."` عند الحاجة. وعندما يكون أي منها مفتوحاً فعلاً، فضّل رفع decision gate دائمة على التخمين؛ ولا تسجّل افتراضاً ذاتياً في `design.md` إلا عندما يفوّض المستخدم صراحةً أو يكون غير متاح، مع وسمه كافتراض بحاجة لتأكيد
- بوابات القرار وخيارات brainstorm ملك للمستخدم: لا تختر `recommended` تلقائياً ولا تحلّ بوابة بنفسك. اعرض كل بوابة عبر سلّم القدرات — واجهة أسئلة أصلية للـ harness (في Claude Code: `AskUserQuestion`)، وإلا واجهة خطة/موافقة، وإلا `Chat Prompt` من decision report في المحادثة — وانتظر إجابة المستخدم الفعلية؛ والبوابات required تحجب التنفيذ و`ospec execute dispatch` على كل harness، فلا تتخطَّ السؤال أبداً
- وعندما يحتاج الاتجاه أو البنية أو API أو UI أو المخاطر أو النطاق إلى ذلك الاختيار، سجّل durable decision gate عبر `ospec execute decision [changes/active/<change>] --id <id> --question "..." --option id:label:impact --option id:label:impact [--recommended id] [--required]`، ثم سجّل الإجابة عبر `--select <option-id>`؛ وتظهر القرارات required المعلّقة في bootstrap/status/finish وفي `artifacts/agents/decisions/index.md` وتحجب dispatch حتى تُختار أو تُتخطى
- في Claude Code يعيد الهوك المُدار حقن هذا العقد وقت التشغيل ويحجب إرسال الـ subagents بصرامة طالما هناك قرار required معلّق؛ ثبّته عبر `ospec session hook --target claude --apply`. هذا الهوك تسهيل خاص بـ Claude فوق القاعدتين أعلاه وليس مصدرهما أبداً: فـ `ospec session hook --target` لا يقبل أي harness آخر، ولذلك تبقى القاعدتان مُلزِمتين من هذه الوثيقة وحدها على Codex وGemini وGrok وOpenCode وCursor وCopilot — وعلى Claude Code قبل تثبيت الهوك
- في goal أنشئ `implementation-plan.md` أو حدّثه من `design.md`، مع الملفات المستهدفة والنتائج المتوقعة وأوامر التحقق والاعتماديات والعمل القابل للتوازي والتعارضات
- في goal اشتق `artifacts/agents/task-graph.json` من `implementation-plan.md`؛ ويجب أن تتضمن كل مهمة id والحالة والاعتماديات وسلامة التوازي والتعارضات والملفات المستهدفة وأوامر التحقق والنتيجة المتوقعة ودور worker. اضبط `parallelizable: true` لكل مهمة لا تتداخل `target_files` الخاصة بها مع مهمة جاهزة أخرى ولا تعتمد عليها؛ واترك `parallelizable: false` فقط عند تعارض الملفات أو وجود اعتماد حقيقي، وسجل `serial_reason` و`conflicts_with`. لا تجعل المهام متسلسلة افتراضيا، وسجل `maxParallelReason` عند تقييد graph آمن إلى worker واحد. قسّم task التي تتجاوز ستة `target_files`، أو أضف `scope_reason` واضحاً عندما يتطلب نطاق تحقق ذري واحد هذا الاتساع. يجب أن يكون كل `depends_on` ضرورياً دلالياً — تعامل combined planning review السلسلة المتسلسلة بالكامل بلا مبرر كـ finding. عندما تبلغ implementation action موزعة عن `serialBottleneck` (كل المهام المتبقية تنتظرها)، يجوز للـ controller تنفيذ تلك المهمة مباشرة في الجلسة الحالية (executor id هو `controller-inline`) بدلاً من spawn subagent؛ وتبقى reviews مستقلة. يسمح `ospec loop configure --review-gating optimistic` بتوزيع المهام التابعة أثناء تشغيل task review الأعلى، ويبقى final review بوابة؛ حافظ على strict الافتراضي لأهداف `high_risk`/`security_related`
- تستخدم allowlist الاختيارية الاستبدال الآمن. عند طلب حد إضافي استخدم `ospec loop allowlist derive/check/apply --from-task-graph`، وراجع فرق CAS، ووافق صراحة على توسيع الصلاحيات المقصود. القرارات required تحجب التنفيذ دائماً؛ وallowlist تضيف حداً fail-closed فقط ولا تنشئ مستوى عمل آخر.
- تستخدم مرحلة design/plan deterministic inline preflight ثم combined planning review مستقل واحد. يسمح بمحاولة grouped planning repair واحدة وإعادة مراجعة تفاضلية واحدة كحد أقصى؛ فشل المنفّذ دون تعديل محتوى التخطيط يعيد تسليح الإصلاح دون استهلاك الحصة، وبعد اكتمال الإصلاح تُقبل النتائج التي لا تتجاوز medium حتمياً كـ `APPROVED_WITH_CONCERNS`، وبعد فشل دلالي متكرر يتوقف المسار بثبات.
- يجب أن تتقارب عمليات review repair. ترث task downstream التي تعدل ملفات مشتركة التزامات regression من upstream المتعدية. تمثل الجولتان الافتراضيتان عتبة تقارب. يستمر التنفيذ عندما تتغير structured finding IDs، ولا يستمر المعرف الثابت إلا عند تغير structured finding fingerprint وcode snapshot المصرح بهما معا. في continuous mode تحصل مجموعة findings المتوقفة للـ task أو final review على strategy escalation دائمة واحدة مرتبطة بالـ scope والمعرفات نفسها؛ نفذ packet إعادة تحليل root cause وfocused regression مرة واحدة، ثم توقف إذا بقيت المجموعة نفسها متوقفة. يحتفظ strict mode بالحد المضبوط. عندما تكون final review بحالة `BLOCKED` يجب التوقف لحل blocker وعدم بدء grouped repair. لا ترفع الحدود لتكرار عمل لم يتغير، ولا تخترع معرف finding جديداً، ولا تعِد صياغة الدليل فقط لفرض repair أخرى.
- يجب أن يكون انتظار native child محدوداً في كل harness. يعيد `wait_agent` في Codex/GPT وpolling لـ Claude Task و`get_command_or_subagent_output` في Grok Build وأي native wait آخر التحكم خلال `maxWaitMs` (60 ثانية) ما دام هناك عمل آخر قابل للتوزيع؛ وعندما تكون pending batch هي العمل الوحيد المتبقي يمكن تمديد idle wait واحدة حتى `idleMaxWaitMs` (10 دقائق). حد الانتظار يقيد انتظار controller واحداً وليس تشغيل child. طالِب بكل child مرة واحدة عبر أمر heartbeat، ثم شغّل `ospec loop poll` بين الانتظارات بدلاً من tick كاملة — تجدد poll كل leases المطالب بها (لا حاجة لأمر heartbeat دوري أثناء polling) وتبلغ عن `tickNow`؛ لا تشغّل `loop run --once` كاملة إلا عندما تبلغ poll عن `tickNow=true` أو مباشرة بعد توزيع batch جديدة. عند الاكتمال استخدم `loop finalize` الصادر مع action لحفظ evidence وresult ذرياً؛ أي item اكتملت أدلته الموثوقة يسوّى تلقائياً في tick التالية، ويقتصر `loop result` اللاحق على استكمال استخدام tokens. عند غياب capacity يستخدم implementation التوازي الافتراضي وهو ثلاث مهام من دون تقليل توازي review الآمن. إذا كان harness يعرف بثقة capacity حالية أكبر للـ child فيمكنه ربطها بجلسة controller النشطة ورفع `maxParallel` وفقاً لذلك؛ لا تخمّن capacity ولا تعِد استخدام قيمة قديمة.
- فضّل تنفيذ جولة controller واحدة على شكل batch. ينفّذ `ospec loop step [changes/active/<goal>] --batch-file <path|->` كامل الـ batch — كل claim وكل result — ثم يجري tick داخل **عملية واحدة**، ويُصدر batch الإجراءات التالية بصيغة compact JSON. وهو يحل محل `loop heartbeat` × N و`loop finalize` × N و`loop run --once`: من 7 استدعاءات controller إلى 2 وفق قياس فعلي عند التوازي الافتراضي 3. والحد الأعلى هو `2C+1` بدلالة السعة **المعلَنة** C (عند C=5 القياس 11)، وليس بدلالة عدد المهام، فالمكسب لا يزداد بزيادة عدد المهام. أرسل `{"claims":[...]}` مع `--no-tick` مباشرة بعد التوزيع، ثم `{"results":[...]}` عند انتهاء الـ children. تبقى كل الأوامر المفردة عاملة. أي مفتاح ناقص أو مكتوب خطأ في الـ envelope يُعد فشلاً صريحاً ولا يُقرأ أبداً على أنه batch فارغة؛ وعند فشل جزئي يتوقف الأمر ولا ينفّذ tick، ويطبع بدقة العناصر التي أصبحت durable بالفعل حتى تستبعدها إعادة الإرسال.
- فضّل تقارير worker وقرارات review المهيكلة. يأخذ `ospec execute complete <task-id> --report-file <json>` الحقول `status` و`summary` و`changedPaths` و`evidence` و`concerns` من مستند JSON واحد مُتحقَّق منه، ويولّد العرض البشري بصيغة Markdown في `artifacts/agents/worker-reports/<task-id>.md`؛ لا تكتب ذلك الملف يدوياً عند استخدام `--report-file`، ولا تمرر `--status`/`--summary` معه. ويقوم `ospec execute review-decision --review <artifact> --decision-file <json>` بإغلاق review صادرة وكتابة `*.findings.json` المرافق، فتصبح كل severity صريحة — إذ تُقرأ review المكتوبة بـ Markdown فقط على أنها `severity: unknown`، وهو ما تعتبره بوابة التخطيط حاجزاً. تظل مسارات Markdown اليدوية عاملة لدورة إصدار واحدة.
- تجدد كل `ospec loop poll` ناجحة (أو tick كاملة) lease القصيرة لـ child حي ومطالب به من دون تمديد absolute deadline؛ وتجدد poll الصريحة lease حتى بعد idle wait طويلة، لذا تعبر leases فترات `idleMaxWaitMs` بأمان. تبقى النتائج المتأخرة المباشرة للمطالبات المنتهية مرفوضة، وتنتهي items المفقودة فعلاً، ولا يتحرك absolute deadline. يجب تنفيذ prerequisite review المفقودة قبل إعادة محاولة dependent work القابل للإعادة. لا يقبل cross-task finding paths إضافية إلا إذا كانت مملوكة لمهام مكتملة ومعلنة في task graph؛ جمّد scope الكامل وأعد review للمالكين المتغيرين. ما دام أي cross-task owner مسجل غير معتمد، تسبق review أو repair الخاصة به أي implementation جديد أو retryable worker، مع بقاء reviewers الآخرين غير المتعارضين متوازيين. قبل full Docker Compose rebuild من دون أسماء خدمات، اقرأ release guidance للمشروع واستخدم أسماء خدمات صريحة عند وجود خدمات غير مرتبطة.
- عند بدء أو استئناف active Goal واحد، استخدم `ospec execute bootstrap [changes/active/<goal>]` لكتابة `artifacts/agents/bootstrap.json` و`artifacts/agents/bootstrap.md` مع project session brief snapshot، ثم اتبع الإجراء الآمن التالي المسجل فيه؛ وعند وجود active dispatch يوصي bootstrap بأمر `ospec execute launch ... --task ...` المطابق
- عند نقل change بين agents أو tools أو worktrees أو shells أو operators بشريين، استخدم `ospec execute handoff [changes/active/<change>] [--target codex|gpt|claude|gemini|grok|opencode|cursor|copilot|shell|generic]` لكتابة `artifacts/agents/handoff.json` و`artifacts/agents/handoff.md`؛ يسجل هذا الأمر project session brief snapshot وtool mapping وقواعد السلامة فقط ولا يشغّل workers أو يعدّل source files
- قبل اشتقاق task graph، شغّل `ospec execute preflight [changes/active/<change>] --stage design` ثم `--stage plan` لإنشاء deterministic inline preflight packets وapproval artifacts تتضمن project session brief snapshot. اشتق أو حدّث task graph بعد نجاح المرحلتين فقط. لا تشغّل الأوامر reviewer child أو shell command ولا تزامن worker status ولا تعدّل source files، واجمع red test العادي وproduction implementation ودليل green/refactor في atomic task واحدة إلا إذا كان test harness نفسه مخرجاً مستقلاً قابلاً لإعادة الاستخدام
- قبل توزيع عمل المهام، استخدم `ospec execute status [changes/active/<change>]` أو `ospec execute next [changes/active/<change>]` لفحص حالة controller والمهام التالية الآمنة
- عند الحاجة إلى تسليم الأمر التالي الموصى به إلى إنسان أو AI، استخدم `ospec execute route [changes/active/<change>]` لكتابة `artifacts/agents/workflow-route.json` و`artifacts/agents/workflow-route.md`؛ هذا الأمر يسجل workflow routing artifacts فقط ولا يعدّل source files.
- قبل handoff إلى worker استخدم `ospec execute workspace [changes/active/<change>]` لكتابة `artifacts/agents/workspace-status.json` و`artifacts/agents/workspace-status.md`؛ عند استئناف Goal قائم، تُقبل فقط المسارات المتسخة التابعة لأهداف task غير `PENDING`، أو ملف `tsconfig.tsbuildinfo` الدقيق داخل حزمة task بدأ فعلا وصرح بأمر build/typecheck، أو لإثبات `ospec update` حالي متحقق من الهاش، وتظل أي مسارات أخرى `needs_isolation`
- قبل إنشاء git worktree معزول، استخدم `ospec execute worktree [changes/active/<change>] [--branch name] [--path path] [--base ref]` لكتابة `artifacts/agents/worktree-plan.json` و`artifacts/agents/worktree-plan.md`؛ وضع plan يسجل خطة تحضير فقط ولا يشغّل git. ولا يُشغَّل `git worktree add` إلا بتمرير `--create` صراحة، ولا `git worktree remove` إلا بتمرير `--cleanup` صراحة؛ وكلاهما يكتب `artifacts/agents/worktree-runs/`، وcleanup لا يحذف الفروع
- قبل الإغلاق النهائي، استخدم `ospec execute finish [changes/active/<change>] [--target main] [--remote origin]` لكتابة `artifacts/agents/finish-plan.json` و`artifacts/agents/finish-plan.md`؛ هذا الأمر يسجل الجاهزية ونص الأوامر فقط ولا يشغل finalize أو archive أو push أو merge أو حذف worktree. عندما تكون حالة finish plan هي ready ولا توجد required pending decision، شغّل `ospec finalize [changes/active/<change>]`؛ استخدم `ospec archive ... --check` كمعاينة dry-run اختيارية فقط ولا تتوقف بعد نجاحها
- الإغلاق تلقائي عند الجاهزية: عندما ينجح `ospec verify [changes/active/<change>]` ولا توجد required pending decision، شغّل `ospec finalize [changes/active/<change>]` بنفسك——لا تتوقف بعد نجاح `ospec verify` أو `ospec archive ... --check` (الـ `--check` معاينة فقط) ولا تنتظر طلب المستخدم. لا توقف الإغلاق إلا حين تحتاج بوابة فعلاً إلى إنسان: required decision غير مُجابة، أو blockers حقيقية يبلّغ عنها verify أو archive، أو طلب صريح من المستخدم للمعاينة أو الموافقة قبل الأرشفة
- التغييرات المؤرشفة أدلة مجمدة: لا تحرر أبداً أي ملف تحت `changes/archived/` (state.json أو المستندات أو artifacts). يزامن CLI البيانات الوصفية من المصادر الموثوقة وقت الأرشفة؛ إذا بقي تعارض فأبلغ عنه بدلاً من إعادة كتابة التاريخ — يشتق knowledge index من المستندات الموثوقة ويعالج cache نفسه ذاتياً
- الأرشفة القسرية استثناء بتفويض صريح من المستخدم وليست مسارا احتياطيا تلقائيا. أبلغ أولا عن كل البوابات الفاشلة وعناصر `NOT_VERIFIED`. يجوز بقاء pending Loop pointer فقط عندما تكون كل item مسجلة نهائيا كـ `completed` أو `failed` أو `expired`؛ أما الحالة المفقودة أو `issued` أو `running` فتمنع الأرشفة. ثم شغّل `ospec finalize [changes/active/<change>] --force-archive --confirm-force-archive <exact-change-name> --reason "<accepted risk>"`. لا تحول الفشل إلى نجاح؛ يبقى الأرشيف incomplete وaccepted-risk.
- استخدم `ospec execute dispatch [changes/active/<change>] [--task task-id] [--limit N]` لإنشاء batch آمن للتوازي من worker packets و`artifacts/agents/execution-session.json`؛ يتضمن كل packet project session brief snapshot وworker profile يوضح capability tier وrecommended target وtarget tool mapping وrationale وrequired behavior. استخدم `ospec execute complete <task-id> ...` لتسجيل نتائج worker. استخدم `--task` لمهمة واحدة صريحة و`--limit` لتحديد حجم dispatch batch. تزامن هذه الأوامر أيضا `artifacts/agents/worker-status.md`، وتحدّث OSpec artifacts فقط ولا تشغّل workers خارجيين؛ عندما تكون النتيجة `NEEDS_CONTEXT` أو `BLOCKED` يكتب `complete` ملفات blocker escalation تحت `artifacts/agents/blockers/`
- لا تضع القبول الخارجي أو اليدوي في المسار الحرج لمهام تنفيذ غير مرتبطة. إذا كان التنفيذ الدائم مسجلاً وكانت المهمة `BLOCKED` فقط لغياب القبول الخارجي، وبعد تفويض المستخدم الصريح لتأجيله إلى البوابة النهائية، شغّل `ospec execute defer-blocker <task-id> [change-path] --reason "..."`. تبقى المهمة محظورة وغير محددة، ويستمر فقط التنفيذ الآمن من ناحية التبعيات؛ وتظل final review وverify وfinalize وarchive محظورة حتى توفر الدليل الحقيقي
- توفير الـ tokens (لا يغيّر أي خطوة ولا أي بوابة): مرّر `--brief` على `ospec execute …` و`ospec loop status`، وقُد كل خطوة من الحالة المختصرة ومسار packet الصادر بدل إعادة قراءة `task-graph.json` أو `worker-status.md` أو `launch-plan.md` أو وثائق goal كاملة في كل دورة. واقرأ prior findings sidecar وملخص الحل قبل إعادة فتح تاريخ المراجعة الكامل — تُكتب الـ artifacts كاملةً على القرص، فافتحها فقط عند الحاجة للتفاصيل
- بعد dispatch، استخدم `ospec execute launch [changes/active/<change>] [--task task-id] [--target codex|gpt|claude|gemini|grok|opencode|cursor|copilot] [--dry-run] [--json]` لكتابة launch plan؛ يقبل `runtimeAdapter` فقط model-native subagent capability حالية ومرتبطة بالـ target. ينشئ single-task dispatch هذه الخطة تلقائيا
- نفّذ `runtimeAdapter.selected.nativeSubagent` وشغّل safe batch فقط بالتوازي. عند غياب capability أو انتهاء صلاحيتها يجب block من دون agent CLI أو fallback إلى current controller
- `IDE-CONTROLLER-AUTO-DISPATCH`: تستخدم كل Goals مسار fast quality واحدا قابلا للتنفيذ. يملك IDE AI دورة tick -> تنفيذ كل `actions[]` عبر model-native subagents -> مطالبة كل child مرة واحدة -> `loop poll` بين الانتظارات -> tick كاملة فقط عند `tickNow=true`. إذا كانت `actions[]` فارغة مع وجود `pending` فهي حالة مراقبة: انتظر/poll فقط ولا يعاد التوزيع. وفي وضع controller لا تتوقف بعد التهيئة ولا تطلب من المستخدم تشغيل أوامر Loop: شغّل `ospec loop run [change] --once --compact-json`، ونفّذ كل action صادرة عبر `runtimeAdapter.selected.nativeSubagent` الخاص بها، وتابع دون مطالبة المستخدم مرة أخرى — وسلّم كل worker مسار packet بدل لصق الـ goal كاملاً
- أزيل agent CLI execution. تفشل `execute orchestrate` و`launch --run --command` و`review --run --command` و`loop watch` قبل تشغيل process أو إنشاء run artifact. استخدم `ospec execute retry` لإعادة native work؛ وتتطلب المهام المكتملة `--force` صراحة
- في Goal مملوكة لـ controller، استخدم `ospec loop tick [changes/active/<change>]` بعد اكتمال كل worker task لإنشاء مراجعة موحدة مرتبطة بـ executor provenance الحقيقي وحزمة محدودة النطاق. استخدم `ospec execute review ... --task <task-id>` مباشرةً فقط خارج controller Loop
- تربط task review المسار canonical الدقيق `artifacts/agents/worker-reports/<task-id>.md` لنفس المهمة داخل target snapshot. يمكن لـ repair تعديل هذا report الدقيق للمهمة نفسها فقط؛ تبقى تقارير المهام الأخرى وأي controller artifacts عشوائية محظورة. إذا أشارت legacy finding إلى canonical report غير موجود في snapshot القديم، نفّذ fresh task-review action التي يصدرها Loop قبل repair ولا تعدّل historical evidence يدوياً
- عند تفعيل `documentation_updates` في task graph، يجب أن تحتوي كل مهمة على المصفوفة (`[]` عند عدم الحاجة)، وأن يظهر كل مسار docs معلن أيضا في `target_files` للمهمة نفسها، وأن يملك دليلا على تغير فعلي بين dispatch وcomplete. يعد الحذف الذي تمت مراجعته تغييرا صالحا عندما يثبت evidence أن baseline موجودا أصبح مفقودا عند الإكمال. عبر محاولات repair المتعددة يقارن finalize أول baseline بالحالة النهائية المكتملة، ويشترط أن تطابق workspace أحدث evidence لمالك المسار المعلن، لذلك لا يكفي تغيير قديم ولا يمر التراجع اللاحق. إذا غير controller closeout مسارا معلنا بعد آخر worker dispatch، فلا تعتمد الحالة النهائية إلا مراجعة task لاحقة بحالة APPROVED، وexecutor provenance صالح، وtarget snapshot يطابق الملف الحالي تماما؛ ولا تحل هذه المراجعة محل meaningful-change chain. تبقى التشغيلات القديمة بلا baseline متوافقة فقط عندما تظل الوثيقة المعلنة موجودة، وتعرض الدليل كغير متحقق.
- قد تُكتب مدخلات `documentation_updates` نيابة عنك: يحقن `ospec docs obligations --apply` مسار مستند كل التزام مطلوب في المهام التي تحمل المصفوفة، ويسجّل `path#section` المحلولة في `state.json.docs_obligations`. اقرأ الالتزام نفسه لمعرفة القسم المطلوب تحريره؛ المصفوفة تحمل مسارات مجردة لأن البوابة تحلّها على القرص. ويقبل التزام نوع التحقّق (refactor / perf، وكذلك `verify_decision` لارتباطات design و`verify_structure` لارتباطات project) فرقًا صفريًا مع `ospec docs confirm --id <معرّف الالتزام>`؛ ويُرفض هذا التأكيد على كل نوع آخر. صنف الارتباط يحدد عقده: أقسام `feature`/`api` تُحدَّث أو تُراجَع حسب change_type؛ وقسم `design` (قرار/ADR) لا يفعل تحت أنواع التغيير البرمجية سوى التحقق من أن القرار ما زال قائمًا، مع وضع Superseded عند نقضه؛ وقسم `project` (البنية/النظرة العامة) يتحقق من دقة البنية بالطريقة نفسها؛ ووثائق `planning`/`product` لا تولّد أي التزام.
- بعد اعتماد task-level reviews واكتمال task graph، دع `ospec loop tick` التالي ينشئ final review في controller Loop؛ استخدم `ospec execute review` من دون `--task` فقط خارج controller Loop
- بعد أن يحتوي review artifact على قرار غير `PENDING`، استخدم `ospec execute feedback [changes/active/<change>] [--stage spec|quality]` لكتابة `artifacts/agents/review-feedback-plan.json` و`artifacts/agents/review-feedback-plan.md`؛ حدد accept أو revise أو clarify أو blocked قبل dispatch عمل إضافي، وأنشئ required user decision gate عندما يغير feedback scope أو direction أو API أو UI أو risk أو accepted tradeoffs
- عندما يكون debugging جزءا من change، استخدم `ospec execute debug [changes/active/<change>] --phase reproduce|isolate|hypothesize|fix|verify --symptom "..." --root-cause "..." --status FIXED` لتسجيل `artifacts/agents/debug-evidence.json`؛ تعني `CONFIRMED` عزل root cause، وتعني `FIXED` إصلاحا متحققا، وتؤدي `BLOCKED` إلى فشل verify؛ وهذا الأمر يسجل evidence فقط ولا يشغّل أوامر shell
- بعد تشغيل focused tests، استخدم `ospec execute tdd [changes/active/<change>] --phase red|green|refactor --command "..." --status ...` لتسجيل `artifacts/agents/tdd-evidence.json`؛ يجب أن تسجل red اختباراً مركزاً غير ناجح قبل التنفيذ، وتتطلب green سجل red بحالة `FAILED` سابقاً، وتتطلب refactor دليل green/refactor ناجحاً سابقاً، وتتطلب `SKIPPED` ملخصاً محدداً؛ وهذا الأمر يسجل evidence فقط ولا يشغّل أوامر shell
- بعد تشغيل project verification commands حديثة، استخدم `ospec execute verify [changes/active/<change>] --command "..." --status PASSED --exit-code 0` لتسجيل `artifacts/agents/verification-evidence.json`؛ لا تدّعِ الاكتمال بمجرد ملخص داخل المحادثة؛ وهذا الأمر يسجل evidence فقط ولا يشغّل أوامر shell
- بعد تعديل task graph أو execution session أو review artifacts أو debug evidence أو verification checklist يدويا، استخدم `ospec execute sync [changes/active/<change>]` لإعادة بناء `artifacts/agents/worker-status.md`
- يجب اشتقاق `tasks.md` من `artifacts/agents/task-graph.json`؛ وإذا كانت المهام موجودة لكن وثائقها السابقة ما زالت قوالب، فحدّث الوثائق السابقة أولاً ثم وائم المهام معها
- لا تؤرشف عندما يحتوي `artifacts/agents/task-graph.json` على حالات مهام غير محسومة أو اعتماديات غير صالحة أو ملفات مستهدفة ناقصة أو أوامر تحقق ناقصة أو تفاصيل تنفيذ ناقصة أو عندما لا يكون `status` العلوي `completed`
- أكمل المراجعة الموحدة الواحدة لكل task (`artifacts/reviews/tasks/<task-id>/review.md`)، ثم أكمل `artifacts/reviews/final-review.md` النهائية الموحدة؛ قرارات task-level أو final review غير المحسومة تمنع الأرشفة
- أثناء التنفيذ والمراجعة، حافظ على اتساق `artifacts/agents/worker-status.md` مع حالات implementer وspec reviewer وquality reviewer وcontroller
- لا تعتبر change مكتملة ما دامت أي حالة worker هي `PENDING` أو `NEEDS_CONTEXT` أو `BLOCKED`؛ ويجب أن تكون `controller_status` هي `DONE` قبل الأرشفة
- استخدم `state.json` كمصدر الحقيقة لحالة التنفيذ
- يجب أن تظهر optional steps المفعلة في `tasks.md` و`verification.md`؛ وفي goal يجب أن تظهر أيضاً في `artifacts/agents/task-graph.json`. كما يجب إدراج كل خطوة مفعّلة نجحت في الحقل `passed_optional_steps` ضمن frontmatter الخاص بـ `verification.md`؛ تتحقق الأرشفة من هذا الحقل وتُحجب ما دامت خطوة مفعّلة غائبة عنه
- زامن `SKILL.md` بعد التغييرات البرمجية المهمة وأعد بناء `SKILL.index.json` عند الحاجة؛ ولا تعتبر العمل مكتملاً عندما تكون ملفات `SKILL.md` والفهرس غير متزامنة

## سياسات السياق والإصلاح

- شغّل deterministic preflight للتصميم والخطة، ثم اشتق task graph، ثم نفّذ combined planning review مستقلة واحدة؛ يسمح بإصلاح تخطيط مجمّع واحد وإعادة مراجعة تفاضلية واحدة كحد أقصى. يعيد فشل المنفّذ دون تعديل التخطيط تسليح الحصة، وتُقبل النتائج التي لا تتجاوز medium حتمياً كـ `APPROVED_WITH_CONCERNS` بعد الإصلاح؛ لا يبطل اعتماد التخطيط إلا تغيير دلالي في محتواه، ولا يبطله تقدم التنفيذ.
- يجب أن تعكس قوائم التقدم الواقع: علّم كل معيار قبول في proposal.md فور نجاح دليل التحقق الخاص به؛ البنود الموسومة بـ `[verify:<id>]` يعلّمها `ospec execute sync` تلقائياً بعد نجاح دليل `--satisfies <id>` المطابق، وتُحظر الأرشفة ما دامت في proposal.md بنود غير معلّمة. ملف review.md في Goal ملخص مشتق يعيد `ospec execute sync` كتابته من final review؛ لا تحرره يدوياً.
- تربط `.skillrc.workflow.model_profiles` ملفات `mechanical` و`standard` و`strong_reasoning` و`review` و`final_review` المنطقية بنماذج target؛ وعند غياب الربط يستخدم harness default مع warning في packet. وتُحل الـ profiles مقابل dispatch target الفعلي بما في ذلك تجاوزات launch. افصل requested/configured model عن provider-observed model؛ فبدون دليل provider/usage يبقى observed model غير معروف ولا يُعلن مختاراً بالادعاء.
- يستخدم command runner المتغير `OSPEC_USAGE_FILE` لجمع normalized usage تلقائيا، ويبقى `--usage-file` كتجاوز يدوي. يجمع `execution-metrics.json` حسب capability tier وmodel profile وworkflow stage ويسجل المصدر والحقول المرصودة وتغطية complete/partial/missing، فلا يُعرض عدّاد غير مبلّغ عنه كصفر مقاس.
- يجب تسجيل كل review finding قابل للتنفيذ أيضا في `*.findings.json` المجاور بمعرف ثابت وseverity وcategory وmessage ودليل file/line ومراجع المتطلبات ونطاق الإصلاح. تعد structured findings التالفة حالة blocking ولا يسمح بالتراجع الصامت؛ ويحوّل Markdown القديم إلى sidecar متوافق قبل repair.
- بعد الأرشفة يجب أن يحمل `docs/project/feature-catalog.md` سطراً واحداً لكل ميزة معلنة، وأن يربط `SKILL.index.json.archived_changes` كلا من دليل change المؤرشف ووثائق المشروع الدائمة الموجودة والمعلنة في المهام. ولقراءة القسم الواحد الذي يصف سلوكاً ما، استخدم `ospec docs locate --feature <slug>` أو `ospec docs locate --affects <path>` بدلاً من فتح الفهرس كاملاً.
- يكتب finalize/archive إدخال `SKILL.index.json.archived_changes` للتغيير المؤرشف (حاملاً `features` و`doc_updates`)، ويحدّث صفوف `docs/project/feature-catalog.md` المتأثرة، ويستبدل تعليق التتبع `<!-- ospec:last-change ... -->` في أقسام الميزات المعنية بشكل idempotent — فشل كتابة التعليق ينتج تحذيرًا فقط ولا يعطّل الأرشفة أبدًا. لا يُنشأ أي ملف تحت `docs/project/changes/`؛ اعرض التغيير المؤرشف عند الطلب عبر `ospec changes show <archive>`. تعليق التتبع هو الكتابة الوحيدة التي يجريها المحرك في وثيقة يملكها البشر، ولا يحل محل وثائق architecture أو API أو module أو operation المطلوبة.
- ينشئ `ospec execute repair [change-path]` repair task واحدة بكل findings فقط عندما يكون final review هو `NEEDS_CHANGES`. حل القرارات required أولاً، ثم نفّذ عبر بوابات dispatch وcomplete وtask review وfinal review القائمة verification واحدة شاملة وtask review واحدة وfinal re-review واحدة.
