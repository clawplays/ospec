# بروتوكول Classic Change

استخدم هذا البروتوكول المختصر عندما يختار المستخدم OSpec change (`ospec change` / `ospec-change`، ويبقى `ospec new` alias). اختيار profile للمستخدم؛ لا ترفع change تلقائياً إلى Goal ولا ترفضها أو تستبدلها بسبب التعقيد أو flags أو عدد الملفات أو المخاطر أو حجم الدفعة، ولا تستخدم `ospec goal` / `ospec-goal` إلا عندما يختار المستخدم Goal صراحة.

طبقة التحكم `ospec execute …` وكل artifacts الخاصة بـ goal تنتمي إلى `workflow_profile_id: goal`: في change لا تقرأها ولا تشغّلها ولا تنشئ ملفات خاصة بـ goal ما لم يرقِّ المستخدم العمل صراحة. يبقى أمر `ospec execute decision` المشترك وحده متاحاً لاختيارات المستخدم الدائمة.

## السياق

في البداية اقرأ `.skillrc` و`proposal.md` و`tasks.md` و`state.json` فقط؛ واسترجع عناصر الفهرس ذات الصلة عبر `ospec index query <كلمات...>` بدلاً من قراءة `SKILL.index.json` كاملاً. اقرأ `verification.md` عند التحقق و`review.md` عند closeout. `state.json` هو مصدر الحقيقة لحالة التنفيذ: عند اختلاف مستند عن `state.json` وفّق الحالة نحو `state.json` بدل الإبلاغ بقيمة المستند.

هذا الملف هو عقد classic كاملاً، ولا توجد فيه قاعدة تعيش في مكان آخر فقط، فلا حاجة للرجوع إلى `for-ai/execution-protocol.md` (فهو طبقة تحكم goal ويجب ألا يفتحه هذا الـ profile). وإذا كان هذا الملف غائباً فاستخدم `for-ai/ai-guide.md` للعودة إلى بروتوكول الـ profile النشط.

## دورة الحياة

1. أنشئ العمل الجديد عبر `ospec change <change-name> [path]`، ويبقى `ospec new` alias للتوافق. تعرض الأداة feature مرشحة **ولا تطبّق أيًا منها تلقائيًا** — أكّدها فورًا: مرّر الـ slug ذات الصلة عبر `--feature <slug>` أو اكتبها في `features:` داخل `proposal.md`؛ وإن لم يوجد مرشح مناسب فاترك القائمة فارغة واستكملها أثناء التخطيط. هذه القائمة تقود آلية التزامات التوثيق بأكملها؛ وتجاهلها يحوّل كل التزام إلى اختياري.
2. إذا وُجد active change مطابق فتابعه ولا تنشئ نسخة مكررة.
3. تدخل تغييرات batch إلى queue وتُنفذ بالتتابع في worktree المشترك. يجب استخدام worktree تسلسلياً: يُحظر الإغلاق (verify/finalize/archive) عند وجود ملفات غير مودعة خارج نطاق `affects` وعقد التوثيق في proposal، لذا أودع أو خزّن أو اعزل التغييرات غير المنسوبة، وصرّح بـ `affects` بصدق، ولا تدع تعديلات جلسة متزامنة تنزلق إلى الأرشيف.
4. حافظ فقط على `proposal.md` و`tasks.md` و`state.json` و`verification.md` و`review.md`، واشتق `tasks.md` مباشرة من `proposal.md` ونطاق التنفيذ، ولا تنشئ design أو plan أو task graph أو worker أو review provenance artifacts الخاصة بـ Goal.
5. شغّل فحوص المشروع المرتبطة فعلاً بالتغيير وسجّل الأوامر والنتائج في `verification.md`، ولا تفرض build أو lint أو test أو TDD أو debug غير ذي صلة. يجب أن تظهر كل خطوة اختيارية مفعّلة في `tasks.md` و`verification.md`، وأن تُدرج الخطوات الناجحة في الحقل `passed_optional_steps` ضمن frontmatter الخاص بـ `verification.md` — تتحقق الأرشفة من هذا الحقل وتُحجب ما دامت خطوة مفعّلة غائبة عنه.
6. ينفذ AI الحالي مراجعة خفيفة واحدة. يمكن إغلاق `APPROVED` و`APPROVED_WITH_CONCERNS` تلقائياً، بينما توقف `PENDING` و`NEEDS_CHANGES` و`BLOCKED` الإغلاق.
7. استخدم `ospec progress` لمتابعة الحالة. شغّل `ospec verify` عند الحاجة إلى preview صريح. بعد اكتمال التنفيذ والتحقق وسياسة الوثائق والمراجعة، شغّل `ospec finalize` فوراً لمزامنة classic state والأرشفة بشكل ذري.

## سياسة الوثائق

اضبط `change_type` على `feature` أو `fix` أو `refactor` أو `perf` أو `deprecate` أو `remove` أو `docs`. ولا تزال الصيغتان القديمتان `bugfix` و`maintenance` مقبولتين وتُطويان إلى `fix` و`refactor` على الترتيب. واضبط `documentation_impact` على `none` أو `required`.

- يمكن للـ bugfix استخدام `none` مع `documentation_reason` واضح، إلا إذا غيّر سلوك المستخدم أو API أو عقد التشغيل.
- يجب أن تستخدم feature أو docs change القيمة `required` وأن تسجل وثيقة مشروع أو module أو API أو user حقيقية واحدة على الأقل في `documentation_updates`.
- لا يُحتسب ملخص `docs/project/changes/...` الموروث من الإصدارات القديمة (لم يعد OSpec ينتجه) كوثائق feature.
- حدّث `SKILL.md` فقط عند تغير قواعد module أو تعليمات AI أو عقود الاستخدام.
- يعاد بناء `SKILL.index.json` تلقائياً بعد archive وليس task يدوية.

### وثائق الميزات

وثائق الميزات الحية هي `docs/features/<domain>.md`، بقسم `##` واحد لكل ميزة. يملكها البشر وتحررها أنت داخل change، والمحرك لا يكتب نصها أبداً.

أعلن الميزة داخل القسم: في أول سطر غير فارغ تحت عنوانها، ولا مكان آخر. لا توجد قائمة `features:` في frontmatter الملف — يبقى ربط الـ slug بالقسم محلياً فينجو من نقل القسم ولا تنشأ نسخة ثانية من الحقيقة نفسها.

```markdown
## Login timeout

<!-- ospec:feature login-timeout code:src/auth/,src/session/ -->

الغرض والسلوك وتدفق المنطق والحدود.

<!-- ospec:last-change 2026-08-14-fix-login-timeout -->
```

- الـ slug بصيغة kebab-case صغيرة (`^[a-z0-9]+(-[a-z0-9]+)*$`) وفريد على مستوى المشروع كله. التكرار يُفشل `ospec index build` ويسمي الموقعين معاً.
- `code:` اختياري ويسرد بادئات مسارات نسبية لجذر المستودع، مفصولة بفواصل، بدون مسافات وبدون شرطات مائلة عكسية.
- القسم الذي لا يحمل إعلاناً ليس ميزة ببساطة. هذا مسموح وليس خطأ.
- يمتد قسم الميزة حتى العنوان التالي بالمستوى نفسه أو أعلى، لذا تنتمي عناوينه الفرعية `###` إلى الميزة.
- يكتب `ospec archive` تعليق `ospec:last-change` ويستبدله. أبقِ واحداً على الأكثر لكل قسم ولا تصنه يدوياً.

### التزامات التوثيق

يقرّر المحرّك أين يجب أن يوثّق هذا التغيير نفسه، فلا تحتاج إلى البحث. في مرحلة التخطيط نفّذ `ospec docs obligations --apply`؛ كل التزام يحمل بالفعل `path#section` المحلولة.

تُشتق الالتزامات من `change_type` ومن قائمة `features:` الخاصة بالتغيير. عندما تكون `features:` فارغة يلجأ المحرك إلى حلّ `affects` من الـ proposal عبر إعلانات `code:` (نفس مطابقة `docs locate --affects`)؛ الإعلان الصريح يتقدّم دائمًا — الـ fallback مجرد شبكة أمان:

| `change_type` | الالتزام |
|---|---|
| `feature` | حدّث القسم الذي يصف سلوك هذه الميزة وتدفقها، أو أنشئه إن كانت الميزة جديدة |
| `fix` | افتح القسم وتحقق مما إذا كان السلوك الموثّق هو **السلوك الخاطئ قبل الإصلاح**؛ إن كان كذلك فصحّحه. **وعند غياب مستند الميزة يهبط الالتزام إلى اختياري مع اقتراح بإنشائه** — يجب ألّا يُجبَر إصلاح بسيط على تضخيم الوثائق |
| `refactor` و`perf` | نوع تحقّق: تأكّد من أن القسم ما زال دقيقًا وحدّث مسارات `code:` الخاصة به |
| `deprecate` و`remove` | حدّد حالة القسم وزامن الفهرس |
| `docs` | التعديل نفسه هو الالتزام |

يقبل التزام نوع التحقّق **فرقًا صفريًا مع تأكيد صريح**: عندما لا تغيّر إعادة الهيكلة أي سلوك موثّق فعليًا، سجّل ذلك عبر `ospec docs confirm --id <معرّف الالتزام>` بدل إجراء تعديل شكلي. ويُرفض هذا التأكيد على كل نوع آخر من الالتزامات، لأن التزامًا يشهد لنفسه لا يتحقّق من شيء.

القيمة `docs_contract.mode` في `.skillrc` هي `warn` أو `strict`، وتكون `warn` افتراضيًا في دورة الإصدار هذه: يُبلَّغ عن الالتزام غير المستوفى عند بوابة الأرشفة دون أن يمنعها. ويُحسم استيفاء الالتزام بالطريقة نفسها في الوضعين؛ الفارق في النتيجة فقط. ولا يمنع الالتزام الاختياري الأرشفة في أي وضع.

نفّذ `ospec docs audit` دوريًا. فهو يسرد أقسام الميزات التي تغيّرت مسارات `code:` الخاصة بها منذ الأرشيف المذكور في تعليق `ospec:last-change` بينما لم يتغيّر المستند — وهو الانحراف الذي وُجدت الالتزامات لمنعه. الأمر للقراءة فقط ولا يُفشل أي بناء أبدًا.

### ترحيل مشروع قائم

المشروع الأقدم من وثائق الميزات يحمل وثائق مولَّدة لكل change تحت `docs/project/changes/`. لم يعد OSpec ينتجها؛ و`ospec docs migrate` يستبدلها على أربع مراحل. أما `ospec update` فيكتفي بالتنبيه — لا يُرحِّل ولا يحذف أبدًا.

1. **`ospec docs migrate --plan --apply`** (المحرك): يجرد الوثائق القديمة، ويجمّع الأرشيفات في مجموعات مرشَّحة حسب بادئة المسار، ويكتب `docs-migration-plan.json` مع هياكل مسوّدات `docs/features/<المجال>.md`.
2. **هذه المرحلة تنفّذها أنت.** المحرك لا يكتب النص.
3. **`ospec docs migrate --verify`** (بوابة المحرك): يرفض ما دامت هناك أي فجوة.
4. **`ospec docs migrate --finalize --apply`** (مدمِّر): يطبع قائمة الملفات ويسجلها، ثم يحذف.

مهمتك هي المرحلة 2، مسوّدة واحدة في كل مرة:

- اقرأ المادة الخام في المسوّدة، ثم اقرأ الدليل الحقيقي خلف كل بند: استخدم `ospec changes show <اسم-الأرشيف>` للملخص والملفات وأوامر التحقق، واقرأ `proposal.md` و`verification.md` و`review.md` داخل الأرشيف لفهم المنطق. اقرأ أيضًا أي وثيقة كتبها إنسان وتغطي المجال نفسه — إن وُجد وصف جيد فانقله ولا تكرره.
- أعد كتابة كل قسم `##` بوصفه وصفًا لما تفعله الميزة **الآن**: الغرض والسلوك وتدفّق المنطق والحدود. هذا ليس سجل تغييرات: يجب أن يفهم القارئ الذي لم يرَ أي change السلوكَ الحالي. غالبًا تنطوي عدة تغييرات قديمة في قسم واحد، والتغيير الذي أصلح خللًا فقط يحتاج عادة إلى تصحيح جملة واحدة.
- أضف تحت كل عنوان إعلان `<!-- ospec:feature <slug> code:<المسارات> -->`، وسطرًا `<!-- ospec:last-change <اسم-الأرشيف> -->` يسمّي أحدث أرشيف يغطيه ذلك القسم. المرحلة 3 تستخدم هذا التعليق لإثبات أن الوثيقة القديمة صار لها مكان.
- احذف علامات المسوّدة: سطر `status: draft` في الـ frontmatter، وتعليقات `<!-- ospec:migration-draft -->`، وكتلة التعليمات. تظل المرحلة 3 رافضة ما بقيت أي منها.
- أعد التجميع بحرية. تجميع المحرك مجرد تخمين؛ فحين يخطئ عدِّل `groups` و`group` في ملف الخطة، أو انقل الأقسام بين الوثائق.
- بالنسبة إلى تغيير **بلا ميزة باقية** — ترقية اعتمادية أو تراجع أو مهمة عابرة — لا تخترع له قسمًا. اضبط `"historical": true` على ذلك الأرشيف في `docs-migration-plan.json`. هذا هو الإعلان الصريح عن "تاريخ خالص" الذي تقبله المرحلة 3، ولا يضبطه إلا إنسان.
- اسأل المستخدم قبل وسم أي شيء بأنه تاريخي إن لم تكن واثقًا. حذف وثيقة لم يذهب محتواها إلى أي مكان هو بالضبط النتيجة الوحيدة التي وُجد هذا المسار لمنعها.

إعادة تشغيل `--plan --apply` آمنة في أي وقت: فهي تحافظ على وسوم `historical` وعلى إعادة تجميعك، ولا تستبدل أبدًا مسوّدة سبق أن أعدت كتابتها.

## بوابات القرار

بوابات القرار وخيارات brainstorm ملك للمستخدم. لا تختر خيار `recommended` بنفسك ولا تحسم بوابة بنفسك — فـ `recommended` تلميح تعرضه على المستخدم وليس اختياراً يحق لك أخذه.

اعرض كل بوابة عبر سلّم القدرات بهذا الترتيب: واجهة سؤال أصلية في الـ harness إن وُجدت (Claude Code `AskUserQuestion`، Gemini `ask_user`)، وإلا واجهة plan/approval الخاصة به (مثل وضع plan في Codex)، وإلا نص `Chat Prompt` من تقرير القرار في المحادثة مباشرة. في كل الحالات تسأل المستخدم فعلاً وتنتظر إجابته الحقيقية؛ ما يختلف هو العرض فقط، والقرار المعلّق من نوع required يحجب التنفيذ والإغلاق بالطريقة نفسها على كل harness. اسأل سؤالاً واحداً في كل مرة.

سجّل البوابة الدائمة عبر `ospec execute decision [changes/active/<change>] --id <id> --question "..." --option id:label:impact --option id:label:impact [--recommended id] [--required]`، ثم سجّل إجابة المستخدم عبر `--select <option-id> --answered-by user`. أمر decision المشترك هذا هو أمر `ospec execute …` الوحيد المتاح لـ classic change. وإذا شغّلت `ospec brainstorm` فلا تتركه قالباً بلا إجابات: سجّل كل إجابة عبر `ospec brainstorm resolve [path] --brainstorm <id> --gate <gate-id> --select <option-id> --answered-by user`.

لا تفتح بوابة إلا عند تفرّع حقيقي: أشكال API متعارضة، مقاربات UI متنافسة، اختيارات نموذج بيانات أو تخزين، عمليات تدميرية أو صعبة التراجع، أو تعارض في النطاق مع ما طلبه المستخدم. أما العمل الروتيني غير الغامض فخذ فيه الخيار الافتراضي المعقول وسجّل الافتراض في `proposal.md` بدل فتح بوابة.

في Claude Code يعيد الـ session hook المُدار حقن هذا العقد أثناء التشغيل ويحجب إطلاق subagent ما دام هناك قرار required معلّق؛ ثبّته مرة واحدة عبر `ospec session hook --target claude --apply`. هذا الـ hook تسهيل خاص بـ harness واحد وليس مصدر العقد: القواعد أعلاه تسري كما هي على Codex وGemini وGrok وOpenCode وCursor وCopilot، وعلى Claude Code قبل تثبيت الـ hook.

## الأرشفة القسرية

الأرشفة القسرية استثناء بتفويض صريح من المستخدم، وليست مساراً احتياطياً تلقائياً، ولا تُستنتج من الاستعجال أو من blocker أو من طلب «أنهِ العمل».

1. أبلغ المستخدم أولاً بالبوابات الفاشلة وبكل عنصر `NOT_VERIFIED` حتى يكون قبوله مبنياً على معرفة.
2. بعد قبول المستخدم الصريح لهذا العمل غير المكتمل فقط، شغّل `ospec finalize [changes/active/<change>] --force-archive --confirm-force-archive <exact-change-name> --reason "<accepted risk>"`. ويفرض الـ CLI بنفسه تأكيد الاسم الدقيق وسبباً غير فارغ.
3. احفظ أدلة الفشل و`NOT_VERIFIED`. الأرشفة القسرية تتجاوز بوابات الاكتمال فقط: تبقى الفحوص الفاشلة والحالة المعلّقة كما هي، ويبقى الأرشيف incomplete وaccepted-risk، ولا يجوز أبداً وصفه كسلوك مكتمل.

توقف فقط لقرار مستخدم حقيقي أو فشل تحقق أو review غير محلولة أو pause صريح.
